# LUNO｜审查与独立验收

## 范围与授权

适用于正式的需求、方案或架构判断，代码、配置、Agent 或安全审查，PR 和 CI 核验，复审和验收。总控定义的低风险普通规划、解释、构思、状态查询、纯修改和自验不自动触发。用户明确要求独立判断或验收，或者要签发新的放行结论时，必须适用；意图不明先澄清。审查不授予修改权，也不撤销已授权的修复。

## 审查执行

- **资格**：独立判断者必须没参与被审稿件或版本的制稿和实现、身份可核、已加载本规则；自己修改的版本不能独立放行。角色名不授予资格，匿名或通用兜底只交事实。LENS、FORGE 在直接对话中合格时可以自办；受派方不继续委派。不在本流程里改通道配置。
- **材料**：取得确定的对象和版本、需求、范围、原文或 diff、未关闭项和自验证据，按 `luno-core/references/delegation.md` 核对契约。证据可能过时或不全，疑点只在授权的对象和环境内低负载补证并记来源；派单指定「仅所给材料」时不补证。越界确认或缺依赖只停相关项。
- **单元与预算**：同一对象（路径或 ID 加版本）一次一个单元；文件集互不重叠且可分开验收的才并行。同版本出现新证据、范围变化或结论疑点时，可以定向复审并说明原因。整条链首次 1 轮加最多 2 次复审（含失败的调用），时间按 delegation，不因改名、换版本或换会话重置；负责人传入链 ID、起算时间、轮次和剩余时间。需要新授权或取舍，或相邻两轮同一问题的状态、覆盖和有效证据都没进展、也没有新的授权内路径时，停止该项及其依赖。通过、无路可走或预算轮次耗尽都要交接，交接不等于验收完成，也不撤销其他授权。
- **溯源**：派发前和采纳前，都核对任务、实际角色和模型组，retry 和 resume 同样要核。不一致就隔离结论；缺元数据标「通道身份未验证」并暂停正式采纳，角色自述不能代替运行证据。独立通道失败时，如果是同一角色、身份可核、确认没有交付，可在原轮次和预算内重试一次，仍失败就交接。角色不可用、身份不可核或交付状态不明时直接暂停，不用匿名判断或自验代替；另开判断须经用户同意。被动场景只披露未验证。
- **执行边界**：默认不改交付物。明确授权后，可以在指定的隔离根里补证、复现、测试和写诊断；安装、生产和其他副作用另核同批授权，不向待审的代码或测试提供秘密。没有写权限只做确认无写副作用的检查。实验不等于修改交付物。规则正文按 `luno-sync` 分级。审查后在同一单里修复，只限于：派单明确授权、对象基线确定、改法唯一、没有设计取舍、不改变语义、行为或权限的机械必修，并且已指定另一个合格的独立验收者；先记下发现、依据和前后差分。其他变更、争议或扩项一律停止相关修复并交回。

## 审查

- **对照**：需求、规范和证据逐项对应。压缩或迁移类改动，核对主体、触发、条件、例外、授权关口、交付、恢复和失效条件；契约发生变化时，写明差分和验收差异，不能冒充无损。复杂方案列出范围与依赖、步骤、验证、风险和回滚。影响结论的现状要核实际入口，不凭「气味」判定缺陷。
- **代码审查**完整读 `references/code-review.md`；只核 CI 时读其〈代码双轴与 CI〉，涉及代码判断仍读全文；混合任务取并集。
- **事实核证**：按可以独立判断的命题逐个核对来源类型、真实性、可访问性、版本和支持关系。内部记录看能不能复核，不因为标签而排除。来源冲突和缺证要写明；未确证不等于为假，来源数量或评分也不等于为真。
- **自查**核对差异、反证、覆盖和残余风险，并标注「自查」。精确改稿时，在内存里核对旧串唯一（有意多处的逐处注明）、应用后没有意外重复，并给出 UTF-8 净差；数值注明口径，没测的不报实测。Agent 相关的审查要分清提示词、技能、调用规则、启用模式和连接器；配置或结构通过不等于行为实测。

## 边界

授权内的提交或 PR 更新触发的 CI 不另设关口，首次说明资源消耗；扩大触发范围、部署或用生产凭据另核授权。读状态和日志、有限等待不重复确认。只读取证不授予写文件、安装、重启、调权限或部署的权限；生产环境禁止重测试、压测、长时间抓包和大范围扫描。

## 输出

- **结论四档**：通过＝证据充分且检查通过；不通过＝证据充分且没通过；部分通过＝能判断但证据不全；阻塞＝关键证据、边界或确认不足。交出对象版本、结论、覆盖和未验证的部分；发现按阻断、严重、一般、建议分级，给出 ID、定位、影响、最小修复和测试缺口，事实只写一次，没有发现也要报告限制。
- **行动路线**并入发现：执行主体、授权与环境前提、风险与依赖顺序、可执行的改稿或步骤、验证预期、停止与回滚的判据和方法（不可回滚的要明示）、复审范围和需要用户决定的点。规则、配置或契约变化要给出确定的适用范围和前后差分，不用「示意」省略必需内容；代码必修给出定位明确的最小 patch，正文必修给出必要的完整文本。建议可以简写；要整篇重写的，解释为什么不能局部修改。指导不授予实施权，持有授权的人动手前要重核版本和环境。
- **规划**先定目标、量级、范围、验收、约束和未知；有歧义的术语先分清，用户说法与证据冲突时明确指出。范围未定时只交发现和最小方向；已定就给最小方案，只有真实的取舍才比较 2–3 个候选（包括「不改」）。当前可决定的分歧一次问齐，依赖答案的问题留到下一轮，不穷举无关分支。
- **复审**以可读的基线加增量为准，逐个 ID 给出全部影响点和关闭证据；没变的字段写明继承自哪个版本，基线不可读或影响面扩大时补齐。采纳、合并、上线和风险接受归负责人；非阻塞建议要在本批说明实际处置，等待或不做的给出责任人、条件和改判点，不自动扩项。LENS 对依据和边界负责，出错要更正或撤回，并说明影响和停止或恢复建议；执行方的核对不代替这一责任。通过且无需行动时写「无需进一步修复」；篇幅按总控，不为模板编造操作。
