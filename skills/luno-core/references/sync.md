# LUNO｜跨端同步与巡检

## 范围

本技能处理**跨端规则对象**（常驻提示词、`luno-*` 与专题技能、子代理指令）在三处落点的同步、巡检和漂移修复：Minis 本地、LobeHub 平台、公开仓库 `LucaLin233/Agent-Sync`。**记忆各端自持，不互相同步**，各端的记忆写法见 `luno-platform/references/minis.md`〔分支 minis〕 和 `luno-platform/references/lobehub.md`〔分支 lobehub〕。

管理落点是 Minis、LobeHub 和公开仓库，运行端是 Minis 和 LobeHub；并不是每个对象三处都有。对象的身份和各端落点只以 `tools/sync-targets.json` 这一份登记为准：某端标为没有的不算漂移，`present` 只表示受管存在，不表示已部署或已核验。正文里不缓存各对象的部署状态，部署沿革见旧私有仓库 `LucaLin233/Agent` 的 git 历史。部署前按明确的 ID 回读目标的实际身份、identifier 和生效字段，与本批已审的基线核对，冲突就停止相关对象并交负责人判定。现在不再做自动的三副本互校和同名发现，所以不能声称已排除额外的同名对象；需要查询时也要有当次授权。

**Minis 内置技能（如 `skill-creator`）不是同步对象**：它们只在 Minis 本地，不进仓库、不上平台，「仓库没有」「平台没有」都不算漂移。判断是否内置要有平台依据；没有入库或映射只表示未受管，不要靠 App 技能页的图标判断。第三方技能在负责人裁定是否同步之前同样不纳入受管集合，不擅自新增落点。

## 资源与触发

路径相对技能根，按总控的加载规则读取：

- 新增、修改、删除或恢复规则对象和规则仓库，工作副本、克隆、并发和发布窗口，部署、归档、巡检、同步脚本和门禁：`references/sync.md`〔分支 sync-workflow〕。第一次改共享真源或仓库之前就要读，不能等到提交或部署时再补。
- 改写规则、提示词或 `description` 的正文：另读 `references/agent-document-writing.md`〔分支 agent-document-writing〕；只查状态或不涉及正文改写的执行不读。
- 新建或适配技能，目录、frontmatter 和校验器：另读 `references/agent-document-writing.md`〔分支 skill-authoring〕。
- 新增、修改或退休测试用例和分层登记，裁定准入和成本预算：另读 `references/test-authoring.md`；只执行既有测试或查状态不读。

## 真源与落点

候选版本在独立的仓库副本里编写，同一个生效对象由当前任务的负责人串行同步（流程见 `references/sync.md`〔分支 sync-workflow〕）。候选不等于生效值；按本批变化的对象回读，并在仓库记录实际的同步状态。

**默认同步授权**：用户已明确确认，本技能范围内所有规则对象（常驻提示词、技能及包内资源、子代理指令与配置）的已授权修改，按 `references/sync.md`〔分支 sync-workflow〕 完成风险分级要求的必要校验和自验，以及需要时的独立放行之后，默认按 `tools/sync-targets.json` 登记的落点完成提交、PR、合并、部署和逐端回读，不逐次征询。这条授权不允许自行新增修改或扩大同步范围。以下情况超出既有授权，仍须确认：新增或删除同步对象，新增端或环境，扩大权限或数据访问面，规则部署以外的生产数据变更，不可逆操作，以及跨端内容冲突需要取舍。秘密面仍按总控。审查或验收没通过就不进入后续阶段；逐端回读、来源登记和实际同步状态的记录都不能省，失败、中断和恢复按既有流程处理，没回读就不算完成。

**生效真源**是 Minis 本地文件：技能是 `/var/minis/skills/<name>/SKILL.md`；常驻提示词有 `/var/minis/memory/SOUL.md` 和 `minis-config` 的 `soul.body` 两处，**以后者为生效值**，两者不一致时先判定当前生效的版本，不自行挑一份覆盖其他。逐处回读判等：

- 常驻提示词：Minis 文件和 `soul.body`、LobeHub agent 的 `systemRole`、仓库 `prompt/`。
- 技能：Minis 文件；LobeHub 的 `content`、`description` 和 `name`（三者独立，按支持的入口分别更新）；仓库 `skills/`。
- 子代理：仓库 `subagents/` 和两端的助理配置。

**上游核对只认 GitHub 仓库**：判断技能有没有上游更新，只比对上游 GitHub 仓库的默认分支 HEAD、目标文件的末次提交和内容哈希，并与本地逐字 diff；不探测技能市场的端点（如 skills.sh 的搜索或下载接口），它们的可用性和返回码不作为来源依据。**来源例外**要逐个对象裁定并登记：目前只有 `luno-surge`，它的官方 Agent Skill 只随 Surge Mac 应用包分发，取源方式、包身份校验（bundle id、版本、build）和逐文件 sha256 判据写在 `luno-surge/references/SOURCE.md`。例外只对该对象有效，不外推，也不能用同名的第三方仓库冒充官方来源。

**巡检和复制**：巡检输出里「内容不一致」指本地与仓库不一致，「与平台不一致」才是平台侧的问题。同步技能文件用单文件内容复制，不用整目录 `cp -r`：它曾把文件 mode 改成 755 污染 git；已经漂移的按 `git ls-files -s` 恢复索引中的 mode。

## 输出

列出同步对象、三处落点的核对结果、差异分类（本地与仓库、与平台）、未覆盖的项和回滚方式；没回读就不算完成，没实测的写明。

# 规则变更与同步流程

## 风险分级

改规则或提示词前先定级；定级不授予写权限，拿不准或有争议的按高风险处理。

- **非行为低风险**：只改错别字或排版（不改变解释）、删除精确重复、移动来源说明，或把同一义务逐字搬到别处且加载闭包、触发和适用范围不变；须能逐项证明主体、条件、例外、权限、行为、恢复和交付义务都没变。可在已授权的独立候选里直接实施，完成必要校验和差分自验后，由负责人核验采纳，不强制独立预审或独立验收。用户或领域明确要求独立判断时照办。
- **行为或存疑高风险**：改变安全、授权或秘密边界、加载或路由、角色或派发、审批或执行语义、恢复义务、领域严格门禁或专业能力，或不能证明没有行为变化的改写，均按行为改动处理。可在已授权的独立候选里直接编写；完成必要校验和自验后，提交确定基线、完整差分、自验证据和回滚办法，经一次最终差分独立审查通过、负责人核验采纳后，才合并或部署，不另设改前预审。本分支自身的修改仍属行为改动；尚未生效的规则不得豁免当前批次。

分级理由、实际 diff 和逐项义务对照写进本批 PR；无法证明非行为时，在合并和部署前按行为改动完成一次最终差分独立放行。独立资格、身份溯源、结论和降级按 `luno-core/references/review.md`〔分支 review〕。只同步内容未变且已满足该级要求的版本时，不重开审查；出现影响原结论的版本、证据或范围变化时，按 review 定向复核，预算不重置。

## 同步顺序

**独立副本或分支上修改 → 必要校验 → GitHub 原生 PR → 串行合并 → 备份将被覆盖的对象 → 按合并的变化同步 → 逐端回读。**不使用自研的发布状态机、冻结链、摘要账本、档案窄提交或机器证据回执；不要求每次正文同步都跑全仓重测试或全端巡检。

1. **副本**：每个会话用独立 clone 和唯一任务分支；Minis 上的候选放在 `/var/minis/shared/agent-sync-candidates/<会话标识>/`，不放 `workspace/`，也不用共享 `.git` 的 worktree。一份副本只有一个写入者；各会话只推自己的分支和 PR，不推 main，不写共享集成副本。由负责人指定的收口者逐个合并，并串行部署同一生效对象。原生 PR 承载差分和合并冲突，但不声称能自动解决语义冲突或平台竞态。
2. **校验**：先读本批 diff 和 `PENDING.md`，核对授权、变化对象和登记落点。只跑变更路径命中的必要测试（以 `tests/run-tests.sh` 的选路为准），纯正文改动跑 `smoke`。`tools/sync-all.sh` 只跑结构守卫和包内校验，不读生效端；rc=1 或 3 阻断，rc=2 只是提示。登记或公共工具变化时，完整执行它们的实际消费者。结构守卫只查加载边、资源边、登记身份、包内引用和义务块是否存在，不比对正文；防止正文弱化靠本文件的分级和独立审查。新增或退休资源要在同批更新 `tools/sync-targets.json`；必需加载的入口变化时，同批更新 `tools/check-rules.py` 的 `REQUIRED_LOADS`。
3. **提交、PR 与合并**：审阅暂存 diff，显式 `git add <本批路径>` 后普通提交，推到本会话任务分支（不强推），用 `gh pr create` 开原生 PR。合并前读最新 main；基线前进就普通 merge main 到本分支，逐处处理冲突并重跑受影响的测试，不用 union、整份选边或强推。收口者确认上一个 PR 已合并后再合下一个。
4. **备份**：只同步已授权的变化对象及其包内资源，按 `tools/sync-targets.json` 找目标；未登记的先登记，不顺带改无关的端。覆盖前备份目标的**实际生效前态**（正文、资源和将改的元数据）到本批资产目录，核对可读、内容和权限；不拿候选副本冒充前态。不要求全仓恢复包或预演未改对象的恢复。
5. **写入**：按平台支持的入口写入，默认同步授权和例外见本技能〈真源与落点〉。写入前核对目标实际生效值仍与已核基线一致；发现并发变更就停止相关对象并重核差分，需取舍时回到确认。LobeHub 同一 identifier 优先原位更新保留 ID；只有无法原位更新且明确授权迁移时，才备份后重建并联动来源登记。Minis 只改正文不需刷新登记，frontmatter 或元数据变化按平台技能流程处理。秘密不进入诊断、备份清单、提交或派发材料。
6. **回读**：对**本次变化的对象**在各登记落端回读：正文和资源逐字节一致，name、description 等变化字段另核；提示词同时核对生效字段和文件视图。不用安装成功、HTTP 200、CI 变绿或文件存在冒充一致。端间允许过渡态；失败只停相关对象，列明已同步和未同步的部分，保留真实前态和恢复办法，不报整批完成，不盲目重投。恢复写入也须在授权内。

不提供全端聚合巡检或「未变豁免」参数。MCP 按本批授权直接核对涉及的配置；URL 参数值不输出，只投影参数名和工具选择状态。普通正文同步不自动扩项。没访问或没核验的端和 MCP 明确写「未核验」，不声称已通过。

## 本仓库的合并与署名

- **只用 squash 合并**：用户已就本仓库明确授权，批准合并即包含删除该 PR 的源分支，所以用 `gh pr merge --squash --delete-branch` 收口，不需另行确认；删除只限该 PR 自己的源分支，用户声明保留的照办，失败如实记录，不扩大清理范围。合并后用 `gh api` 回读 merged 状态、main 上的提交（应为单父、Committer 是 GitHub web-flow 且已签名）和源分支已删除。远端再次前进就重新核对差分，不盲目重投。
- **squash 提交说明**（合并时填写的标题和正文，会随合并落库）：为 PR 内**每个提交的 Author**，以及去重后的 `Co-authored-by`，各写一行 `Co-authored-by: 名 <邮箱>`。身份取自 PR 提交的原始字节（`git cat-file commit`），不按平台显示的账号名改写。
- **身份判定**：署名身份见 `luno-core/references/review.md`〔分支 delegation〕〈Git 提交署名〉。普通提交的编写身份按 Author 和合法的 `Co-authored-by` 的并集去重判定：同一身份写了多行、或多个提交属于同一人，只算一次，不判违规；但普通提交的尾行与 Author 相同仍判违规。只有 squash 提交允许尾行与 Author 相同（它的 Author 是 PR 内最后一个提交的作者，按原字节逐行写时必然重合）。平台自动生成的合并和 squash 提交不要求、也不另加作者行。
- **机械检查**：提交后、推送前，必须运行 `python3 -B tools/check-commit-identities.py --base <已核的基线提交> --head HEAD` 并通过，CI 再按 PR 的 base..head 复核。push 到 main 时，检查器放行「单父、Committer 是 GitHub web-flow 且签名经 `tools/github-web-flow.gpg` 验证通过」的提交，同时要求它的 `Co-authored-by` 非空且逐条合规；空范围、缺行或不实署名都判违规，不因为是 squash 就豁免。
- 只从确认已合并的版本取变化对象部署；仓库合并不等于线上同步成功，没部署或部分成功都要如实记录。共享集成副本只由收口者在干净状态下快进更新，其他会话不写。开 PR、合并和实际部署分别核对既有授权，校验脚本不会自动执行这些写入。

## 记录与恢复

本批 PR 一次性记录对象和改动、实际校验、提交和远端回读、各端部署和回读，以及未完成的状态；正式的独立审查附上对象版本和脱敏后的结论。合并后据实补充 PR，不为补记另开 PR 或提交，也不预先填写成功。不再维护 changelog，也不在 PENDING 里归档全文副本；历史以 git 为准，不清理恢复证据。

活动中的未决事项只放在 `PENDING.md`：写对象、条件或承接的批次、责任人和必要的恢复指针。新一批只复检相关的项；本批已授权的工作直接做完，不列等待。决定不做的记在本批 PR 里（理由、改判条件、责任人），条件没变就不重开；只能等真实场景的被动观察只披露未验证，不挂待办。

记录里不写秘密、主机名或本机路径。合并前发现的错误在原分支修正后复核；中断或失败时，先核对工作区、远端和已改目标的实际状态，再按授权接续或恢复，保留实际前态和恢复限制。

## 变更纪律

改动前定位源头、引用方、登记和必要的副本。声明改稿或副本与某个源片段「同文」「逐字一致」时，自验、所需独立审查和改后回读均须按明确的片段边界和既定的正文提取口径，用程序比对 UTF-8 字节，不自行去前缀、strip 或归一换行。改完回读所有目标，报告旧→新、UTF-8 净差，以及实际运行的测试集合和耗时，不拿计数当覆盖。规则真源和字段判等按本技能入口；候选不等于生效值，尚未部署的规则不改变当前的执行边界。改动以最小为先，优先净减；保留有意的冗余，不借精简削弱秘密、授权、隔离和写后回读的要求。

**来源与许可**：第三方吸收件的运行正文须留必要作者/许可、改写性质及来源登记指针；完整上游仓库@提交、路径、日期、取材边界和可取性记在 skills-sources.md 或该对象包内来源登记，许可全文仍随包分发。仅下沉详细来源不删除证据或扩大分发权；新增吸收/退役另核对象授权，缺来源不称完成。

**主动补规则**只有一种例外：问题在本会话里已经发生、造成了后果、因果已经核实，并且该文件已有维护授权。缺任何一项都只能把建议交给发起方，禁止自行写入。巡检诊断按总控的源头投影只取非秘密字段；完整恢复备份不能用来取密或交互输出。
