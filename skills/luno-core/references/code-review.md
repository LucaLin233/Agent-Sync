# 代码审查

本文件含改写自 `anthropics/knowledge-work-plugins` 与 `anthropics/claude-plugins-official` 的内容（Apache-2.0，已修改；许可见 `../LICENSE.code-review.txt`、`../LICENSE.apache-2.0.txt`）。

通用流程、授权、分级和输出按 `references/review.md`〔分支 review〕；实施侧纪律（最小改动、沿用风格、只清自己引入的孤儿代码、先复现后修复、重构保持行为、结果证据）按 `luno-authoring/references/coding.md`〔分支 coding〕。通用检查面（设计、功能、复杂度、测试、命名、注释、风格，以及安全、性能和依赖）按 [Google 代码审查指南：审查看什么](https://google.github.io/eng-practices/review/reviewer/looking-for.html) 逐文件覆盖；这里只写代码审查的分轴、CI 和本机取舍。

## 代码双轴与 CI

代码审查的两条轴（Standards 规范、Spec 需求）默认由同一个 LENS 分别完成；这是检查和报告上的分轴，不代表独立上下文或并行审查。派发材料要给出被审版本、比较基线或 diff 范围、仓库规范和原始需求的确定引用；规范按被审目录的适用范围核对。Standards 轴区分成文规范的违例、已证实的缺陷和启发式「气味」，气味不能只凭名称阻塞。Spec 轴逐项检查遗漏、部分或错误的实现和范围蔓延；需求来源缺失时只暂停依赖它的验收项，用户明确说没有 spec 时标「不适用」，不写 Spec 通过。安全、性能、正确性和可维护性的覆盖仍要做。

两条轴分别交出依据、结论和未验证的部分；发现标明属于哪条轴，跨轴只引用 ID，不另报各轴的发现数、最高严重度或优点栏。整体结论按必需的验收条件和影响定为通过、不通过、部分通过或阻塞，不跨轴排名；复审仍交两条轴各自的本轮结论。有证据的优点可以简记，不强求。

CI 核对最新的 HEAD、实际运行的套件和日志。GitHub 查询按 `gh pr checks`、`gh run view --log-failed`、`gh run watch --exit-status` 当前的 `--help` 只取最小字段，必要时用 `--json`/`--jq` 和经授权的 `gh api --paginate`；watch 外层要设时限，pending 的退出码 8 既不算失败也不算通过。CI 变绿不代替完整验收，也不等于生产实测；新增 unittest 用例时，要核对正常入口实际跑到的用例数和预期集合（含跳过项）。范围内的缺口如果有修复授权，由持有授权的主助理或执行角色继续修复和验证。提交后有限等待 CI，期间可以并行做独立审查，代码修复后可以重跑。没有代码变更时，只有已确认是 runner 中断、平台故障这类瞬时的基础设施故障，才在既有授权内说明依据、预设次数和时限后有限重试；状态不明、非幂等或疑似真实的测试失败要先取证，不靠重试刷绿，也不放宽断言。

## 本机判据

- **静默失败**：对宽泛 catch 或多级 fallback，具体指出它隐藏了什么错误、有什么可观察影响；质疑无理由的 `any`/`unknown`/可选/强制转换/静默兜底。
- **复杂度**：数读者须同时持有的概念、层次与状态。抽象值不值按 `luno-authoring/references/coding.md`〔分支 coding〕〈改动〉核对，重复次数只是线索，不按「第三次出现」自动要求或否决；删除或合并抽象后，核复杂度移到了哪里、调用方是否少持有该概念，避免只是换位置。变更体量按影响和逻辑内聚判断，行数不是否决门槛，必要的生成代码、性能展开和边界层不因长而否决。结构发现须有证据并给具名最小改法，不见气味就不重构。
- **依赖**：新增前先核现有栈能否解决、体积、维护活跃度、已知漏洞及许可证兼容；优先标准库与既有工具。升级逐包隔离审查并读 changelog（semver 不保证无破坏）；升级前后测试均须通过，覆盖薄弱须列为发现；关注传递依赖，lockfile 诚实提交、不手改。
- **测试**：先审测试，看它测的是行为还是实现、能否抓回归；测试建议要说明会抓哪类回归。期望值不得按被测代码的同一算法重算（如 `add(a,b)` 断 `a+b`、手抄同一推导的快照、常量等于自己），须来自需求、可核算实例或独立参考实现；没有独立依据就标测试有效性缺口，不因套件绿色关闭。关键行为或覆盖存疑时，只在获准的隔离副本里做定向变异实验（如去掉取反、`&&` 换 `||`），跑套件后还原副本；先确认变异可达、非等价且确实改变预期行为，不可达或等价的不判缺用例；仍全绿就指出具体缺失的用例。审查者取得隔离根授权可自行实验、不写交付物；未获授权交负责人转授权执行路径，只审阅结果；没有授权或环境就标测试有效性未验证。
- **上下文与反馈**：先弄清变更要解决什么、依据哪个需求、预期行为变化是什么。采纳外部反馈前核当前调用方、平台与既有设计理由，没有实际消费者就不因反馈扩项。架构健康评估先按用户痛点或近期高频变更圈定热点再取证，普通 diff 审查不扫全库历史。核对作者的验证故事：跑了什么测试、构建是否通过、是否人工验证、UI 变更有无前后对比。
- **排序与分歧**：正确性和安全优先，其次结构回归与遗漏的简化；外观 nit 不能埋掉结构问题。不做无证据的通过，不淡化真问题，能量化就量化。分歧按技术事实与数据 > 风格指南 > 工程设计原则 > 代码库一致性；作者有完整上下文并坚持时接受推翻，评代码不评人。
- **收尾**：死代码先列位置和可确认的替代者，清理范围与删除条件按 coding〈改动〉，已授权且确定的删除不重复问，不确定才问，不静默删。当批处理不了的发现按 `luno-core`〈执行闭环〉说明处置与责任；只有已授权且确需外部跟踪时才建 issue，不以口头「以后处理」冒充闭环。
